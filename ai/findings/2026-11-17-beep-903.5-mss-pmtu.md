## 1. Where each figure comes from

`bulk_fetch` (`u7s/scripts/e2e-install/cloud-two-node.sh:690-703`) runs
`ss -tin '( dport = :8081 )'` on the CLIENT VM (the external probe, not a
backend) while `curl` downloads `/f` from cp's front. The bulk pod is pinned
to w1 (`:620`), so data flows w1 pod -> w1 -> Geneve -> cp -> client. The
client is the receiver: its `ss` cannot show the pod's retransmits.

| figure | meaning | derivation |

| v4 `advmss:1408` | MSS the client advertises | 1460 - 40 - 12 (timestamps) |
| v6 `advmss:1388` | same, v6 | 1460 - 60 - 12 |

The pod MTU is 1410 (`cni0` and all veths in `e-mtu-table.log`; flannel's
1460 - 50). On-wire L3 size of bulk segments is 1358 + 12 + 40 = 1410 (v4)
and 1338 + 12 + 60 = 1410 (v6).

The v6 `mss:1208` is the first 1 s sample, taken in `SYN-SENT`

## 3. Oversize handling (kernel claims: upstream knowledge, unverified)

1. `drivers/net/geneve.c` `geneve_xmit_skb` calls `skb_tunnel_check_pmtu(..,
   netif_is_any_bridge_port(dev))`. In `net/ipv4/ip_tunnel_core.c` it lowers
   the inner skb dst PMTU, and sends PTB only when `reply` is true (bridge
   port). geneve0 has no master (`e-mtu-table.log`), so no PTB originates
   from this call. Unverified against 7.0.
2. For collect_md devices DF comes from `TUNNEL_DONT_FRAGMENT`, which
   `bpf_skb_set_tunnel_key` sets only for `BPF_F_DONT_FRAGMENT`
   (`net/core/filter.c`). So outer DF=0 and an over-MTU outer packet is
   fragmented (`ip_finish_output_gso` / `ip_fragment`). Unverified against
   7.0.
3. `ip_forward_use_pmtu` defaults to 0, so v4 `ip_forward` should not emit a
   PTB to the pod from a PMTU exception. Unverified against 7.0.
4. `__bpf_redirect` drops oversize non-GSO skbs via `is_skb_forwardable`,
   silently, no ICMP. geneve0 is 65465, so it never trips in run 1; it
   matters for any fix that lowers geneve0's MTU. Unverified against 7.0.

Open question, v6: `ip6_forward` honours PMTU exceptions, and the tunnel
PMTU check may update the forwarded skb's dst. A PTB to the pod on the v6
path is therefore possible, and nothing in the evidence rules it out (or
in). A dropped GSO skb would appear as a pod-side retransmit that the client
never shows. Run 2 measures it (section 6).

## 4. Does the evidence show PMTUD?

No. `grep -i icmp|pmtu|frag|too big` over `stdout.log` and all logs finds
only `ss` `pmtu:1460` fields and the ping table (cp -> w1 on the underlay,
outside the tunnel). Nothing records the pod's route PMTU, ICMP counters,
IP fragment counters, or a capture. The client `ss` shows no `retrans`, but
that is the receiver and says nothing about the pod. The pod `mss` stayed
1358 / 1338 in the ESTAB samples.

## 5. Production risk

If DF=0 fragmentation is the carrier: v4-outer works wherever the underlay
forwards and reassembles fragments (GCP did), at a packet cost not measured
in run 1, and blackholes where fragments are dropped (stateless filters,
some cloud NAT paths). A v6 underlay has no router fragmentation, has a
94 B overhead (budget 1366, 44 B over), and is entirely untested. Non-TCP
traffic (UDP/QUIC) is unaffected by any MSS fix.
