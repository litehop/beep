# 903 run 1: TCP MSS vs the Geneve budget

Bead: beep-903.5

**Verdict: inconclusive on mechanism, and not "OK as-is".** Run 1's bulk
segments were 1410 B at L3, 24 B (v4) / 44 B (v6) over beep's inner budget
of 1386 / 1366, and crossed the tunnel with no retransmits. Nothing in the
evidence shows PMTU discovery (PMTUD) happening, and by kernel logic no PTB
can reach the backend pod. The likeliest carrier is outer-IP fragmentation
(Geneve outer DF=0), which is unmeasured. Run 2 must add the counters in
the last section. Fix bead: beep-903.6.

Evidence root: `u7s/temp/e2e/hqhd0-beep-run1-20261117/` (`stdout.log`,
dir `20261117T092137Z/`). Kernel on both nodes: 7.0.0-1017-gcp
(`e-mtu-v4/w1/after/kernel.txt`). Kernel-source claims below cite upstream
paths from knowledge; the 7.0 source was NOT read in this session.

## 1. Where each figure comes from

`bulk_fetch` (`u7s/scripts/e2e-install/cloud-two-node.sh:690-703`) runs
`ss -tin '( dport = :8081 )'` on the CLIENT VM (the external probe, not a
backend) while `curl` downloads `/f` from cp's front. The bulk pod is pinned
to w1 (`:620`), so the data flows w1 pod -> w1 -> Geneve -> cp -> client.
Every recorded figure is the client's view of a download; the bulk direction
is backend -> client.

| figure | meaning | derivation |
|---|---|---|
| v4 `advmss:1408` | MSS the client advertises | 1460 - 40 - 12 (timestamps) |
| v6 `advmss:1388` | same, v6 | 1460 - 60 - 12 |
| v4 `mss:1358` | client's SEND mss = pod's SYN-ACK MSS minus ts | pod eth0 MTU 1410 - 40 - 12 |
| v6 `mss:1338` | same, v6 | 1410 - 60 - 12 |
| `rcvmss:1358` / `1338` | largest segment payload the client saw arrive | equals `mss` |
| v6 `mss:1208 advmss:1400` | NOT PMTUD: the SYN-SENT sample | see below |

The pod MTU is 1410: `cni0` and all veths are 1410 in `e-mtu-table.log`
(flannel's 1460 - 50). `mss:1358` therefore is the pod's own choice, and
the on-wire L3 size of bulk segments is 1358 + 12 + 40 = 1410 (v4),
1338 + 12 + 60 = 1410 (v6).

The v6 `mss:1208` is the first 1 s sample, taken in `SYN-SENT`
(`e-mtu-v6.log:22-23`: `SYN-SENT ... mss:1208 ... rcvmss:88 segs_out:1
unacked:1`). 1208 is the pre-handshake default (1220 minus 12), not a
discovered value. The `ESTAB` sample is `mss:1338` (`:26`). The RECORD line
(`:28`) merges the two samples, which makes 1208 look like a reduction.
`pmtu:1460` is the CLIENT's route; no figure here is measured on the pod.

## 2. Return leg: bulk segments are Geneve-encapsulated

Backend replies leave the pod raw (src PodIP, dst client). On w1 the egress
classifier on the uplink (`ebpf/src/main.rs:1872`,
`try_uplink_egress_return_headers_v4` `:1935-2027`; v6 sibling `:2031`)
matches via POD_TARGETS and the reverse FLOW_TABLE row, then
`redirect_to_geneve(..., rev.ingress_node_ip, VNI_RET, opt[24], ..)` with the
24 B front-echo option (`:2008-2026`). `redirect_to_geneve` (`:786-845`)
calls `bpf_skb_set_tunnel_key` with flags from `set_tunnel_remote`
(`:669-685`): `0` for a v4 remote, `BPF_F_TUNINFO_IPV6` for v6; never
`BPF_F_DONT_FRAGMENT`. It then calls `bpf_skb_set_tunnel_opt` and
`bpf_redirect(geneve0)`. Decap and un-NAT on cp:
`try_geneve_decap_return` (`:1578`).

So every bulk segment is encapsulated, under both Cluster and Local (the
bulk Service uses the default policy; the path is the same w1 -> cp hop).
Overhead is `geneve_overhead(.., 24)` (`common/src/lib.rs:355-364`): 74 B v4
underlay, 94 B v6. Both underlays in run 1 were v4 (`10.80.0.x`,
`10.82.0.x`), so a v6 outer was never exercised.

Counters confirm full-size inner segments on the tunnel
(`e-mtu-v4/cp/geneve0-delta.json`, `e-mtu-v6/cp/geneve0-delta.json`):

- cp geneve0 `rx_packets` delta: 77232 (v4), 78485 (v6). 104857600 B / 77232
  = 1358 B/pkt; / 78485 = 1336 B/pkt. This matches `mss` (1358 / 1338), so
  the packets that arrived at cp were individual 1410 B inner packets.
- w1 geneve0 `tx_packets` delta: 2038 (v4), 1765 (v6): the pod sent GSO
  super-skbs (~38-44 segments each), which the kernel segmented after the
  redirect.

## 3. Oversize handling: no PTB reaches the pod

Kernel mechanics (upstream, unverified against 7.0):

1. `drivers/net/geneve.c` `geneve_xmit_skb` calls `skb_tunnel_check_pmtu(skb,
   &rt->dst, GENEVE_IPV4_HLEN + options_len, netif_is_any_bridge_port(dev))`
   (the headroom there includes the inner Ethernet: 14 + 20 + 8 + 8 + 24 =
   74, the same figure as beep's). In `net/ipv4/ip_tunnel_core.c` the
   function only lowers the inner skb dst's PMTU; it sends ICMP/ICMPv6 PTB
   only when `reply` is true (geneve0 is a bridge port) and the skb is not
   `PACKET_HOST`. geneve0 is not a bridge port here (`e-mtu-table.log`: no
   master), so no PTB originates.
2. `df = key->tun_flags & TUNNEL_DONT_FRAGMENT ? htons(IP_DF) : 0` for
   collect_md devices; `bpf_skb_set_tunnel_key` sets that flag only for
   `BPF_F_DONT_FRAGMENT` (`net/core/filter.c`), which beep does not pass. The
   outer packet has DF=0. An over-MTU outer packet (1470 B IP on a 1460 NIC)
   then takes the `ip_finish_output_gso` slow path / `ip_fragment`
   (`net/ipv4/ip_output.c`) and is fragmented. An ICMP "frag needed" is only
   sent for DF=1, and then goes to the outer source (w1 itself), never the
   pod.
3. A pmtu exception left on the pod -> client route could make
   `ip_forward` / `ip6_forward` emit a PTB to the pod on later packets. For
   v4 that needs `net.ipv4.ip_forward_use_pmtu=1` (default 0, so no). For
   v6 whether the forward path honours the exception was not established.
4. The redirect itself (`__bpf_redirect`, `net/core/filter.c`) checks the
   target device MTU for non-GSO skbs and drops silently, with no ICMP, if
   exceeded. geneve0 is 65465, so it never trips in run 1; it matters for
   any fix that lowers geneve0's MTU.

## 4. Does the evidence show PMTUD?

No. `grep -i icmp|pmtu|frag|too big` over `stdout.log` and all logs finds
only `ss` `pmtu:1460` fields and the ping table. The ping table
(`e-mtu-v4/ping-table.txt`) is cp -> w1 on the underlay, outside the tunnel:
max DF payload 1432 / 1412 as expected. Nothing records the pod's route
PMTU, ICMP counters, IP fragment counters, or a capture. Transfer
completed in about 4000 client segments with `retrans` absent from the
`ss` samples; a PMTUD recovery would show retransmissions and a smaller
pod `mss`, neither present. The 1 s sampling could miss early events.

## 5. Production risk

If the DF=0 fragmentation reading is right: v4-outer works wherever the
underlay forwards and reassembles fragments (GCP did), at a cost of ~2x
packets on the return path, and blackholes where fragments are dropped
(stateless filters, some cloud NAT paths). A v6 underlay has no router
fragmentation and `ip6_fragment` honours DF-less only if `ignore_df` is
set; that is entirely untested.
