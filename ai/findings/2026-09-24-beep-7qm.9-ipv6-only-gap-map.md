# IPv6-only-node gap map (beep-7qm.9)

Bead: beep-7qm.9
Date: 2026-09-24
Kind: findings (Shape-3 audit, read-only)

## Answer (read this first)

beep is **not close** to running on an IPv6-only node today: the eBPF/common
dataplane is dual-stack-ready (v0.3.0), but the **controller crate
(`controller/`) — the only code path that runs in a real cluster — is
IPv4-only end to end**, and the eBPF underlay-peer-attestation path is
IPv4-only on its GET side (tracked separately, beep-8b0). The critical path
to a working IPv6-only-node round trip is: (1) widen the controller's own
view types + K8s-JSON parsing + CLI off `Ipv4Addr` (nothing here was touched
by beep-7qm.4-.7 — those beads widened `beep-common`/`ebpf`/the *standalone
loader's* CLI, never `controller/`), then (2) beep-8b0's existing GET-side
eBPF fix, then (3) a controller-driven (not bare-loader-fixture) live
round-trip test — every dual-stack/v6 smoke test that has ever passed
(beep-7qm.3, beep-7qm.7) drove the standalone loader's `--fixture`/`--node-ip`
directly and never exercised the controller's Node/Service/EndpointSlice
watch loop at all.

**Severity counts:** HIGH: 2 · MED: 2 · LOW: 2 · DEFER: 1.

## Findings

### HIGH-1 — controller crate is `Ipv4Addr`-typed end-to-end; a v6-only node is invisible to it

`controller/src/watch.rs:197` (`parse_node_internal_ip -> Option<Ipv4Addr>`,
reading `status.addresses[].type=InternalIP`): on an IPv6-only node this
field holds a v6 literal, `.parse::<Ipv4Addr>()` fails, and the function
returns `None` **silently** — the node never enters `node_ips`
(`watch.rs:80`), never appears in `front_ips` (`watch.rs:370`), and gets no
`NODE_ALLOW`/`LB_FRONT_MAP` entry at all. This is the actual root blocker for
"beep runs on IPv6-only nodes": the node is architecturally invisible to the
one code path that programs the dataplane in a real deployment.

Same root cause, same file, further sites:
- `watch.rs:57` (`RawEndpoint.pod_ip: Ipv4Addr`) + `watch.rs:183`
  (`.parse().ok()?` inside a `filter_map`): an `EndpointSlice` entry with a v6
  pod address is silently dropped from that Service's backend set, no log.
- `controller/src/reconcile.rs:38` (`Ipv4Cidr`), `:100`
  (`NodeContext.node_ip: Ipv4Addr`), `:121` (`ServiceView.vip_ip: Ipv4Addr`),
  `:136-137` (`Endpoint.pod_ip`/`node_ip: Ipv4Addr`) — the pure reconciliation
  logic has no v6 branch; every helper (`is_admitted`, `pod_targets_for_node`,
  `reconcile_service`) is typed against v4 only.
- `controller/src/status.rs:38,79` (`merged_ingress`/`ensure_node_ingress`,
  `node_ip: Ipv4Addr`) — `status.loadBalancer.ingress` can never publish a v6
  address, so a v6 client has nothing to poll even if everything upstream
  worked.
- `controller/src/main.rs:89,96` (`--pod-cidr: Ipv4Cidr`, `--node-ip:
  Option<Ipv4Addr>`) — the controller's own CLI rejects a v6 literal outright
  (clap parse failure at startup), unlike the standalone loader's
  `src/main.rs` (widened to `IpAddr` by beep-7qm.6).

Corroboration from the code's own contemporaneous comment,
`controller/src/apply.rs:302-305` (`describe_node_allow_peer`'s doc comment):
*"every value in play today unmaps cleanly; the fallback is just a legible
stand-in for a genuine v6 peer, **not yet reachable**"* — the maintainer
already flagged, in-line, that the controller has never fed a real v6 value
through the (already `[u8;16]`-shaped, beep-r7l) pinned-map wire layer.

**Not covered by beep-8b0** (which is scoped to the eBPF GET-side attestation
only) or beep-903 (real-fleet sign-off, not implementation). Filed as new
beads (below), ordered first since nothing else in the IPv6-only path can be
exercised through a real cluster until the controller can see a v6-only
node at all.

### HIGH-2 — `geneve_ingress` GET-side reads `remote_ipv4` unconditionally (4 sites, one beyond beep-8b0's own list)

`ebpf/src/main.rs:858` (`try_geneve_decap_forward`'s `NODE_ALLOW.get`),
`:1055` (`try_geneve_decap_forward_v4`'s `RevFlowValue.ingress_node_ip`),
`:1215` (`try_geneve_decap_forward_v6`'s own `ingress_node_ip`, same bug —
the v6 INNER path still reads the v4-only OUTER tunnel field) — all three
already tracked in beep-8b0's description. This audit found a **fourth**
site not in beep-8b0's own file:line list: `ebpf/src/main.rs:1270`
(`try_geneve_decap_return`'s own `NODE_ALLOW.get(ipv4_mapped_v6(tkey.
__bindgen_anon_1.remote_ipv4))`) — the return-leg peer attestation has the
identical gap. Appended to beep-8b0's notes (not a new bead, per dispatch
instruction not to duplicate it).

`set_tunnel_remote`'s v6 SET arm (`ebpf/src/main.rs:449-464`) remains
reasoned-from-kernel-source, not empirically confirmed (module's own doc
comment, `:444-448`) — still true; see "Live check" below for why this audit
did not attempt to close that gap itself.

### MED-1 — Service `ipFamilies`/`ipFamilyPolicy` are never read; open design question once node_ip is dual-stack

Zero matches for `ipFamil` anywhere under `controller/src/`. Harmless today
because beep's node-owned-address model fronts every `type=LoadBalancer`
Service on *every* known node IP regardless of the Service's own spec
(`watch.rs:457-465`) — there is exactly one family in play (v4) so there is
nothing to disambiguate. Once HIGH-1 lands and a node can carry both a v4 and
a v6 `InternalIP`, this becomes a real question: does a `SingleStack,
ipFamilies:[IPv4]` Service get fronted on that node's v6 address too (wrong:
exposes a service the operator scoped to v4 over an unintended family), or
must the controller filter `front_ips` per-Service by its own
`ipFamilies`/`ipFamilyPolicy`? Left as an explicit open design question for
the operator inside the follow-on bead's description, not answered here.

### MED-2 — every existing v6/dual-stack smoke PASS bypassed the controller entirely

beep-7qm.3 and beep-7qm.7 (the two v0.3.0 dual-stack smoke gates) both drive
the **standalone loader's** `--fixture`/`--node-ip` flags directly
(`scripts/smoke-wg-2node-remote.sh`'s `start-loader`), never the
controller's Node/Service/EndpointSlice watch loop. Combined with HIGH-1,
this means there is currently **zero** live evidence that a real Service
object, on a real (even v4-only) cluster, ever produces a correct dual-stack
`LB_FRONT_MAP`/`NODE_ALLOW` — only that the bare loader's fixture path can.
Filed as its own follow-on bead (ordered last, depends on the controller
widening).

### LOW-1 — no v6-underlay smoke rig variant exists; concrete recipe appended to beep-8b0

`scripts/smoke-wg-2node-remote.sh`'s `setup_wg --family 6` (lines ~90-150)
only stands up `wg0`'s own v6 ULA for a bare `ping6`/`nc` connectivity check
(`scripts/smoke-wg-2node.sh:207-233`), then it is torn down before the `4`
setup that actually feeds `start-loader --node-ip` (`smoke-wg-2node.sh:274,
282`). No script has ever passed a v6 literal as `--node-ip`/a fixture's
`backend_node_ip` — i.e., no script has ever driven beep's *own* Geneve
encap/decap over a v6 underlay. Concrete recipe (appended to beep-8b0's
notes, not a separate bead): reuse `setup_wg --family 6` without tearing it
down, widen its WireGuard peer `--extra-allowed` (already exists for the v4
path, `smoke-wg-2node.sh:243-246`) to admit the client's real address in the
v6 CIDR too, then `start-loader --node-ip <v6 ULA>` with a v6-literal fixture
`backend_node_ip`. `tcpdump -i wg0` on the receiving node can confirm the
`set_tunnel_remote` v6 SET arm alone (outer IPv6+UDP+Geneve header well-formed
on the wire) independent of whether the GET-side (HIGH-2) accepts it.

### LOW-2 — `disable_rp_filter` is IPv4-only; empirically not a gap

`src/lib.rs:453-459` writes only `/proc/sys/net/ipv4/conf/{dev}/rp_filter`.
Not a v6 front gap in practice: beep-7qm.7's v6-client dual-stack smoke
already PASSED cross-node with no IPv6 rp_filter-equivalent tweak, so an
inner v6 packet's local delivery is empirically not blocked by anything this
function would need to touch. Linux also has no IPv6 sysctl of the same
name/semantics (`rp_filter` is IPv4-specific, RFC 3704 `fib_validate_source`)
to even set. No action; noted so a future reader doesn't assume this is an
unverified v6 gap.

### DEFER — outer-header MTU/overhead math for a 40-byte v6 outer header

No file in `ebpf/`, `src/`, or `scripts/` computes outer Geneve/IP header
length by hand for *any* underlay family — the kernel's `geneve external`
device plus `bpf_skb_set_tunnel_key`/`_opt` own MTU/fragmentation, and no
script sets or asserts an MTU value anywhere (`grep -i mtu` across
`docs/design/ebpf-lb-dataplane.md` and `scripts/*.sh`: zero hits). A v6
underlay's extra 20 bytes (40B fixed IPv6 header vs. 20B IPv4) is therefore
not a beep-owned computation to audit — but it has also never been exercised
under a near-MTU or jumbo payload on *any* underlay family, v4 included. Not
v6-specific; out of scope for this bead. Worth its own perf/correctness bead
only if real-fleet fragmentation ever becomes a symptom (feeds beep-903).

## Live check

**Not run.** Evaluated against the 30-minute cap and judged not cheap: (1) a
genuine end-to-end round trip over a v6 underlay is blocked by HIGH-2's
GET-side attestation regardless of whether the SET arm is correct, so no
full round trip is achievable without a code change (out of scope for a
Shape-3 audit); (2) a narrower SET-arm-only check (tcpdump the wire, skip
decap) needs the WireGuard peer `allowed-ips` widening described in LOW-1,
which is not covered by any single existing script and could not be
assembled and safely torn down within the cap without risking leaving dirty
state on the assigned VMs. Recorded as the concrete recipe above, appended
to beep-8b0's notes for whoever picks that bead up.
