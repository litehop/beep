# `geneve_ingress` peer attestation checks the LOCAL tunnel endpoint (beep-7qm.14)

Bead: beep-7qm.14
Date: 2026-09-24
Kind: findings (Shape-3 investigation, dataplane bug -- NOT fixed here)

## Verdict: CONFIRMED

On the real 2-node WireGuard rig (`beep-node-a`/`beep-node-b`), `bpf_skb_get_tunnel_key`'s
`remote_ipv4` on RX in `geneve_ingress` is the **receiving node's own tunnel
address**, not the packet's genuine outer sender. `peer_node_admission`
self-matches on every deployment (`populate_fixtures` always seeds a node's
own `--node-ip` into its own `NODE_ALLOW`) and never actually attests a
remote peer. A spoofed Geneve packet with the right VNI, from any source that
can reach `geneve0` (e.g. any host on the underlay with `rp_filter=0`), is
admitted today.

## The decisive evidence

Both reviewer confounds from PR #140's review were controlled for:

1. **No hand-typed keys.** Every NODE_ALLOW key came from
   `dump-node-allow-key` (reads the loader's own already-correctly-encoded
   entry) piped straight into `seed-node-allow`/`bpftool map update` --
   never hand-derived from an IP string.
2. **Self-entry explicitly deleted**, not left alongside the peer key
   (`bpftool map delete ... key <self-entry bytes>` before seeding the peer
   key), so admission was genuinely peer-only, not "peer + self".

Rig: v4 underlay, `beep-node-a` (10.99.0.2/wg0, owns VIP `10.99.0.2:19100`),
`beep-node-b` (10.99.0.4/wg0, backend pod `198.51.100.60:18090`),
`beep-client` (192.168.104.14, relayed through node-b's `eth0` IP-forward).
Built via `cargo +nightly zigbuild --release --target aarch64-unknown-linux-gnu`,
driven directly through `scripts/smoke-wg-2node-remote.sh`'s subcommands
(`setup-wg`, `setup-geneve`, `start-loader`, `setup-backend`,
`start-backend-responder`, `dump-node-allow-key`, `seed-node-allow`) --
same building blocks `scripts/smoke-wg-2node.sh` uses, just driven one leg at
a time instead of via the all-in-one host script.

**Experiment 1 -- pass/fail isolation (matches the bug report's own claim exactly):**

| node-b's NODE_ALLOW | Round trip |
|---|---|
| peer-only: node-a's real key only (`0a630002` host-native), self-entry (`0a630004`) deleted | **FAIL** -- `curl` times out after 20s (SYN retransmits, silently `TC_ACT_SHOT`-dropped) |
| self-only (default from `populate_fixtures`, self-entry `0a630004`, no peer key at all) | **PASS** -- `curl` returns `200 OK` |

This is the opposite of what "seed the peer's key" (the old prescription in
the mayor-dispatch-template / `2-node-wg-rig-fidelity` memory) predicts, and
matches beep-7qm.14's description precisely.

**Experiment 2 -- direct kernel-value proof (removes all inference).** Added
a throwaway `bpf_printk!` in `try_geneve_decap_forward` right after the
`tunnel_remote`/`NODE_ALLOW.get` read (reverted after capture, not part of
this PR's diff), rebuilt, redeployed to node-b only, re-ran the peer-only
NODE_ALLOW case from Experiment 1, and captured `/sys/kernel/debug/tracing/trace_pipe`
on node-b during the client's connection attempt:

```
bpf_trace_printk: INVESTIGATE fwd remote_ipv4=174260228 known=0
```

`174260228` decimal = `0x0a630004` hex = **10.99.0.4 -- node-b's own wg0
address**, not `0x0a630002` (10.99.0.2, node-a's real wg0 address, the
genuine outer sender of every packet in this test). `known=0` confirms the
membership check correctly saw a miss against the peer-only NODE_ALLOW
(which held only node-a's key) -- because the value being looked up was
node-b's own address, never node-a's.

This single value is the crux of the bug: `geneve_ingress`'s GET-side
`bpf_skb_get_tunnel_key` call on node-b, decapsulating a packet node-a
genuinely sent, reports node-b's own local tunnel endpoint as "remote".

## Kernel-source reasoning vs. the empirical result

Read from memory (no kernel source tree on this host to grep against --
flagged explicitly, not verified line-by-line): `net/core/filter.c`'s
`bpf_skb_get_tunnel_key` does `to->remote_ipv4 = be32_to_cpu(info->key.u.ipv4.src)`,
and the generic RX-metadata construction path shared by vxlan/geneve/openvswitch
(`ip_tunnel_key_init`, called from `udp_tun_rx_dst` for an `external`/
`collect_md` Geneve device -- confirmed this rig uses `ip link add geneve0
type geneve external`, `smoke-wg-2node-remote.sh:152`) sets `key.u.ipv4.src`
from the packet's own outer IP source and `key.u.ipv4.dst` from the outer IP
destination. Taken at face value, that predicts `remote_ipv4` on GET should
be the genuine sender (node-a), not local -- the opposite of what was
observed.

I could not reconcile this from memory alone within the investigation's time
box; the observed value is authoritative regardless. Two candidate
explanations, neither confirmed:
- My recollection of `net/core/filter.c`/`ip_tunnel_key_init`'s exact
  src/dst assignment on the RX path is wrong or version-specific.
- Something specific to a WireGuard-relayed, external-mode Geneve device on
  this kernel swaps which field ends up as `.src` (e.g. metadata reuse
  between node-a's own SET-side `tkey` construction and node-b's GET, if
  the two share more state than the two calls' documented contract implies).

Either way: **the fix must not assume the naive kernel-doc reading is
correct** -- it must be re-verified empirically (`bpf_printk` against a live
kernel, same as this investigation) whatever mechanism is chosen.

## Fix options (dataplane fix goes to the operator -- not implemented here)

1. **Read the real outer IP src via a raw `load_direct` at a fixed offset**,
   bypassing `bpf_skb_get_tunnel_key` for attestation purposes entirely.
   Geneve's outer header is UDP/IP, and `geneve_ingress` already runs after
   decap onto `geneve0` -- the packet at that point is the *inner* payload,
   so this requires attaching a second, outer-header-visible hook (e.g. on
   the physical uplink/`wg0` ingress, before decap) to capture the true
   outer src and hand it forward (extra map, or repurpose the existing
   `FWD_PENDING`-style pending-state map) for `geneve_ingress` to check
   against. More invasive (a second attestation point, keyed by VNI/flow),
   but doesn't depend on `bpf_skb_get_tunnel_key`'s undocumented-in-practice
   RX semantics at all.
2. **Find and use whichever `bpf_tunnel_key` field genuinely carries the
   sender on this kernel** (if any) -- e.g. try both `remote_ipv4`-as-dst
   and a possible dedicated "local" field if the kernel/aya binding exposes
   one, and empirically pick whichever field the RX path actually populates
   with the sender. Lowest-effort if such a field exists, but the aya
   `bpf_tunnel_key` binding (`ebpf/src/main.rs`'s `__bindgen_anon_1`) only
   exposes `remote_ipv4`/`remote_ipv6` -- no separate "local" field -- so
   this option may not exist without a wider kernel-side capability
   (`bpf_skb_get_tunnel_key`'s `to_orig`/compat path caps the struct at
   what today's kernel already returns).
3. **Drop the security claim from the docs/design** (`beep_common::peer_node_admission`'s
   doc comment, `docs/decisions/geneve-rp-filter-disable.md`) and rely
   entirely on `rp_filter` + network-level isolation (WireGuard/Tailscale
   mesh membership) as the actual peer-attestation boundary, removing
   `NODE_ALLOW`'s check or demoting it to a non-security-bearing sanity
   check. Simplest, but weakens the stated security model this bead's
   parent thread depends on.

**Recommendation:** option 1. It's the only one that attests the packet's
*actual* wire-observed sender rather than trusting kernel tunnel metadata
whose RX semantics this investigation could not fully explain from source.
It costs a second hook/map, consistent with this codebase's existing pattern
of multiple narrowly-scoped hooks per direction.

## Rig change in this PR

Added an env-flag-gated regression check to `scripts/smoke-wg-2node.sh`
(`BEEP_PEER_ATTESTATION_CHECK=1`), run after the existing default round trip,
that:
1. Seeds node-b's NODE_ALLOW peer-only (node-a's key via
   `dump-node-allow-key`, self-entry explicitly deleted) and asserts the
   round trip PASSES -- the correct post-fix behavior (genuine peer
   attested).
2. Restores NODE_ALLOW to self-only (no real peer key) and asserts a
   packet from the real peer is DROPPED -- the correct post-fix behavior
   (peer not in the allow-list, so not attested).

Both assertions FAIL against today's code (verified: see Experiment 1 above)
-- this is expected and intentional until the dataplane fix lands. It is
NOT wired into the default `scripts/smoke-wg-2node.sh` invocation (the env
flag defaults unset/0), so today's CI gate (which runs the script with no
flags) stays green. beep-7qm.14 stays OPEN; the fix is a separate PR chosen
by the operator from the options above.

## Risks / caveats

- Kernel-source reasoning above is from memory, not a grepped kernel tree on
  this host -- flagged explicitly rather than presented as verified.
- Only the v4 rig (`smoke-wg-2node.sh` default) was tested live; the v6
  branch (`--family 6`) was not re-run in this investigation (time-boxed) --

  (`ebpf/src/main.rs:1301`/`:888`) so the same bug is expected to reproduce
  there, but this is inferred from code, not independently confirmed on v6.
- The throwaway `bpf_printk!` instrumentation used for Experiment 2 was
  reverted (`git checkout -- ebpf/src/main.rs`) before this PR's diff was
  built -- it is not part of the committed change.
