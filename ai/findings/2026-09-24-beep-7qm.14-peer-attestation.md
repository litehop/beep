# `geneve_ingress` peer attestation checks the LOCAL tunnel endpoint (beep-7qm.14)

Bead: beep-7qm.14
Date: 2026-09-24 (revised 2026-09-24, same day, following a decisive
follow-up experiment -- see "Revised verdict" below)
Kind: findings (Shape-3 investigation) -- **the "Verdict: CONFIRMED" section
right below this is WRONG**; it is kept as a record of what the original
investigation observed, but its root-cause attribution is superseded. Read
"Revised verdict (2026-09-24, follow-up)" first.

## Revised verdict (2026-09-24, follow-up): NOT a dataplane bug -- a rig self-loop

`bpf_skb_get_tunnel_key`'s `remote_ipv4` on RX is **not** buggy: confirmed
against this kernel's own `net/core/filter.c` (`bpf_skb_get_tunnel_key`
reads `info->key.u.ipv4.src`, which the RX-metadata constructor
(`ip_tun_rx_dst`/`ip_tunnel_key_init(key, iph->saddr, iph->daddr, ...)`)
populates from the packet's genuine outer source) and against a live
`bpf_printk` capture of a packet that **actually left node-a and crossed
wg0** -- `remote_ipv4` read node-a's real address, and `NODE_ALLOW`
correctly admitted it once seeded with node-a's real key. Neither hypothesis
(a) nor (b) from this bead's dispatch is correct; there is no dataplane fix.

The original "CONFIRMED" evidence below is real (the printk capture, the
pass/fail table) but its interpretation was wrong: `scripts/smoke-wg-2node.sh`
loads the *identical* VIP fixture on **both** nodes. Node-b's own
`uplink_ingress` (attached to its real `eth0`, which is also the client's
IP-forward relay path) matches that fixture just as well as node-a's does,
and `eth0` ingress runs before any IP-forward decision -- so node-b's own
hook always wins the race and Geneve-encapsulates the client's SYN to
`backend_node_ip` = itself, entirely locally. The packet never reaches
node-a, never crosses `wg0` (confirmed: `wg0`'s rx/tx packet counters were
unchanged across the "passing" round trip, and node-a's `FLOW_TABLE` was
empty afterward), and `geneve_ingress` on node-b decapsulates a packet it
just encapsulated to itself -- so `remote_ipv4` trivially equals node-b's own
address for the mundane reason that node-b really did tunnel to itself, not
because the kernel misreports the field. See "Decisive follow-up experiment"
below for the reproduction that isolates this from a genuine cross-node
packet.

**No dataplane fix in this PR.** Revised recommendation: file a follow-up
bead to fix the rig's self-loop (node-b's `uplink_ingress` on `eth0` should
not also claim ingress admission for the VIP it's hosting the backend for),
so `BEEP_PEER_ATTESTATION_CHECK` -- and `smoke-wg-2node.sh`'s "GATE 1 TIER-1
MECHANISM" claim generally -- actually exercises node-a's `wg0`-ingress path
instead of silently short-circuiting on node-b every time.

## Decisive follow-up experiment (kernel source + forced genuine cross-node packet)

**Kernel source, confirmed (not from memory this time):** fetched
`net/core/filter.c` at tag `v6.8` (`beep-node-a`/`-b` both run
`6.8.0-139-generic`) via `gh api repos/torvalds/linux/contents/net/core/filter.c?ref=v6.8`.

```c
// bpf_skb_get_tunnel_key, v4 (non-BPF_F_TUNINFO_IPV6) arm:
to->remote_ipv4 = be32_to_cpu(info->key.u.ipv4.src);
...
to->local_ipv4 = be32_to_cpu(info->key.u.ipv4.dst);
```
```c
// bpf_skb_set_tunnel_key, v4 arm:
info->key.u.ipv4.dst = cpu_to_be32(from->remote_ipv4);
info->key.u.ipv4.src = cpu_to_be32(from->local_ipv4);
info->key.flow_flags = FLOWI_FLAG_ANYSRC;
```

GET's `remote_ipv4` reads `.src`; for an RX-constructed `ip_tunnel_info`
(`ip_tun_rx_dst` -> `ip_tunnel_key_init(key, iph->saddr, iph->daddr, ...)`)
`.src` is the packet's genuine outer source. `aya-ebpf-bindings 0.2.0`'s
`bpf_tunnel_key` (checked directly, all 6 arches) does have a third
`__bindgen_anon_3` union with `local_ipv4`/`local_ipv6` -- the findings
below show this field turns out not to matter for the bug, since there is
no bug in the field beep already uses.

**Forcing a genuine cross-node packet.** Reloaded node-b with a *decoy*
fixture (`10.99.0.2:1:tcp:...` -- wrong front port, same backend/pod) so
node-b's own `uplink_ingress` never matches the client's real SYN
(`dst_port=19100`) and the packet must take the normal IP-forward path
instead, out node-b's `wg0` to node-a. `tcpdump -ni wg0` on **both** nodes
during the client's SYN retransmits:

```
14:28:49.605964 IP 10.99.0.2.54381 > 10.99.0.4.6081: Geneve, Flags [none], vni 0x64, options [20 bytes]:
    IP 192.168.104.14.42660 > 10.99.0.2.19100: Flags [S], ...
```

Outer src `10.99.0.2` = node-a's real address, outer dst `10.99.0.4` =
node-b's real address, VNI `0x64` = 100 = `VNI_FWD` -- node-a's SET path is
correct; there is no encap-side bug (hypothesis (b) refuted). `wg0`'s
rx/tx counters moved by the same delta (+9/+9) on both nodes for this
attempt, unlike the self-looped default round trip (0 movement, see the
"Revised verdict" section above) -- direct proof this packet actually
crossed the tunnel.

With node-b's `NODE_ALLOW` re-isolated to peer-only (node-a's real key,
self-entry deleted -- same protocol as the original Experiment 1) and a
throwaway `bpf_printk!` in `try_geneve_decap_forward` (reverted before this
PR's diff, not committed), `trace_pipe` on node-b during that same forced
cross-node SYN:

```
bpf_trace_printk: INVESTIGATE fwd remote_ipv4=174260226 known=1
```

`174260226` decimal = `0x0a630002` hex = **10.99.0.2, node-a's real
address** -- the genuine sender, not node-b's own (`0x0a630004`). `known=1`:
`NODE_ALLOW`'s peer-only membership check correctly admitted it. This is
hypothesis (a) refuted, directly: `remote_ipv4` on GET reports the real
remote peer, not the local endpoint, once the self-loop confound is removed.
(The full round trip still didn't complete end to end in this decoy-fixture
setup -- the decoy front port also breaks the *unrelated* `TARGET_PORTS`
membership lookup `try_geneve_decap_forward_v4` does later using the
packet's real port, which is a fixture-construction artifact of the decoy,
not a peer-attestation issue -- but that lookup runs strictly after the
`known=1` admission above, so it doesn't affect this experiment's answer.)

## The original (superseded) evidence

Both reviewer confounds from PR #140's review were controlled for:

1. **No hand-typed keys.** Every NODE_ALLOW key came from
   `dump-node-allow-key` (reads the loader's own already-correctly-encoded
   entry) piped straight into `seed-node-allow`/`bpftool map update` --
   never hand-derived from an IP string.
2. **Self-entry explicitly deleted**, not left alongside the peer key
   (`bpftool map delete ... key <self-entry bytes>` before seeding the peer
   key), so admission was genuinely peer-only, not "peer + self".

Rig: v4 underlay, `beep-node-a` (10.99.0.2/wg0, owns VIP `10.99.0.2:19100`),
`beep-node-b` (10.99.0.4/wg0, backend pod `198.51.100.60:18090`),
`beep-client` (192.168.104.14, relayed through node-b's `eth0` IP-forward).
Built via `cargo +nightly zigbuild --release --target aarch64-unknown-linux-gnu`,
driven directly through `scripts/smoke-wg-2node-remote.sh`'s subcommands
(`setup-wg`, `setup-geneve`, `start-loader`, `setup-backend`,
`start-backend-responder`, `dump-node-allow-key`, `seed-node-allow`) --
same building blocks `scripts/smoke-wg-2node.sh` uses, just driven one leg at
a time instead of via the all-in-one host script.

**Experiment 1 -- pass/fail isolation (matches the bug report's own claim exactly):**

| node-b's NODE_ALLOW | Round trip |
|---|---|
| peer-only: node-a's real key only (`0a630002` host-native), self-entry (`0a630004`) deleted | **FAIL** -- `curl` times out after 20s (SYN retransmits, silently `TC_ACT_SHOT`-dropped) |
| self-only (default from `populate_fixtures`, self-entry `0a630004`, no peer key at all) | **PASS** -- `curl` returns `200 OK` |

This is the opposite of what "seed the peer's key" (the old prescription in
the mayor-dispatch-template / `2-node-wg-rig-fidelity` memory) predicts, and
matches beep-7qm.14's description precisely.

**Experiment 2 -- direct kernel-value proof (removes all inference).** Added
a throwaway `bpf_printk!` in `try_geneve_decap_forward` right after the
`tunnel_remote`/`NODE_ALLOW.get` read (reverted after capture, not part of
this PR's diff), rebuilt, redeployed to node-b only, re-ran the peer-only
NODE_ALLOW case from Experiment 1, and captured `/sys/kernel/debug/tracing/trace_pipe`
on node-b during the client's connection attempt:

```
bpf_trace_printk: INVESTIGATE fwd remote_ipv4=174260228 known=0
```

`174260228` decimal = `0x0a630004` hex = **10.99.0.4 -- node-b's own wg0
address**, not `0x0a630002` (10.99.0.2, node-a's real wg0 address, the
genuine outer sender of every packet in this test). `known=0` confirms the
membership check correctly saw a miss against the peer-only NODE_ALLOW
(which held only node-a's key) -- because the value being looked up was
node-b's own address, never node-a's.

This single value is the crux of the bug: `geneve_ingress`'s GET-side
`bpf_skb_get_tunnel_key` call on node-b, decapsulating a packet node-a
genuinely sent, reports node-b's own local tunnel endpoint as "remote".

## Kernel-source reasoning vs. the empirical result (superseded by the follow-up above)

This section is kept for the record; its "predicts the opposite of what was
observed" framing is resolved by the follow-up experiment above -- the
kernel source's prediction (GET reports the genuine sender) was right all
along, and what was "observed" in Experiment 1/2 below was a self-looped
packet, not a genuine cross-node one.

Read from memory (no kernel source tree on this host to grep against --
flagged explicitly, not verified line-by-line): `net/core/filter.c`'s
`bpf_skb_get_tunnel_key` does `to->remote_ipv4 = be32_to_cpu(info->key.u.ipv4.src)`,
and the generic RX-metadata construction path shared by vxlan/geneve/openvswitch
(`ip_tunnel_key_init`, called from `udp_tun_rx_dst` for an `external`/
`collect_md` Geneve device -- confirmed this rig uses `ip link add geneve0
type geneve external`, `smoke-wg-2node-remote.sh:152`) sets `key.u.ipv4.src`
from the packet's own outer IP source and `key.u.ipv4.dst` from the outer IP
destination. Taken at face value, that predicts `remote_ipv4` on GET should
be the genuine sender (node-a), not local -- the opposite of what was
observed.

## Fix options (superseded -- no dataplane fix; kept for the record)

The three options below were drafted assuming a real dataplane defect. The
follow-up experiment found none, so none of these are being implemented.
Revised recommendation: file a follow-up bead for the rig's self-loop (see
"Revised verdict" above) instead.

1. **Read the real outer IP src via a raw `load_direct` at a fixed offset**,
   bypassing `bpf_skb_get_tunnel_key` for attestation purposes entirely.
   Geneve's outer header is UDP/IP, and `geneve_ingress` already runs after
   decap onto `geneve0` -- the packet at that point is the *inner* payload,
   so this requires attaching a second, outer-header-visible hook (e.g. on
   the physical uplink/`wg0` ingress, before decap) to capture the true
   outer src and hand it forward (extra map, or repurpose the existing
   `FWD_PENDING`-style pending-state map) for `geneve_ingress` to check
   against.
2. **Find and use whichever `bpf_tunnel_key` field genuinely carries the
   sender on this kernel.** Moot: `remote_ipv4` already is that field
   (confirmed above).
3. **Drop the security claim from the docs/design** (`beep_common::peer_node_admission`'s
   doc comment, `docs/decisions/geneve-rp-filter-disable.md`). Not needed:
   the claim holds once a genuine peer's key is seeded, per the follow-up
   experiment.

## Rig change (PR #142, merged) -- superseded by the follow-up above

`BEEP_PEER_ATTESTATION_CHECK=1`, added by PR #142, asserts peer-only
NODE_ALLOW PASSES and self-only DROPS the real peer. Both assertions FAIL
against `smoke-wg-2node.sh`'s default round trip -- but per the follow-up
experiment above, that's because the default round trip self-loops on
node-b and never sends anything node-a's real key would match, not because
`NODE_ALLOW`/`bpf_skb_get_tunnel_key` are broken. This PR leaves the check
opt-in (unchanged) rather than flipping it default-on: there is no
dataplane fix to gate it on, and flipping it on today would just make CI
red against the same self-loop, not against a real regression. It should
move to default-on once the rig's self-loop (see "Revised verdict") is
fixed in a follow-up bead.

## Rig change (this PR)

`scripts/smoke-wg-2node-remote.sh`'s `start_backend_responder`: kills any
prior listener bound to the same `pod_ip:port` before restarting, and fails
loudly if the new one doesn't stay bound. `nc -N` (no `-k`) exits after one
connection, but a case whose request never reached it (e.g. dropped by
`NODE_ALLOW`) leaves it still listening; the next case's restart would
otherwise either fail to bind silently or let the stale listener serve the
next case undetected (caught in review of PR #142, fixed here since this
bead already touches the same file).

## Risks / caveats

- Only the v4 rig (`smoke-wg-2node.sh` default) was tested live; `--family 6`
  was not re-run -- it shares the same self-loop risk (identical fixture on
  both nodes) so is expected to have the same confound, but this is
  inferred, not independently confirmed.
- The decisive follow-up experiment's decoy-fixture setup never completed a
  full end-to-end round trip (a *different*, `TARGET_PORTS`-lookup-based
  drop after the peer-attestation check already passed -- see that
  section) -- sufficient to answer the peer-attestation question, but not a
  general validation that a fully genuine cross-node round trip passes
  today. That validation needs the rig fix recommended above, not this PR.
- The throwaway `bpf_printk!` instrumentation used in both this
  investigation and PR #142's was reverted before either PR's diff was
  built -- not part of the committed change in either case.
